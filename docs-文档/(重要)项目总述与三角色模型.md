# CGHub 项目总述与三角色模型

> 本文用于统一项目叙事、角色边界和核心业务闭环。  
> 结论：CGHub 是一个围绕“活动资金池 + 贡献记录 + 自动分账”的协作结算系统。产品入口应区分三个角色：**项目方 / 用户**、**贡献者**、**管理者**。

---

## 1. 项目一句话

CGHub 让一个活动可以先建立资金池，再记录贡献者为活动带来的代码、组织和传播价值，最后按贡献分数把资金池里的资金分给贡献者。

更短地说：

```text
活动产生资金 -> 贡献者创造价值 -> Agent 评分 -> Cobo 审核分配权 -> 资金池按分数分账
```

---

## 2. 项目解决的问题

很多黑客松、社区活动、开源活动或运营活动都会遇到这些问题：

- 活动有资金，但资金来源、用途和结算过程不够清楚。
- 很多贡献不是单纯代码，还包括组织活动、宣传活动、写文档、拉合作、维护社群。
- 活动结束后，很难公平说明每个贡献者应该拿多少。
- 项目方、活动参与用户、贡献者、管理者经常被混成一个“用户”，导致页面和权限很乱。

CGHub 的目标是把这些问题拆成清晰闭环：

- 管理者负责创建活动和资金池。
- 项目方 / 用户负责为活动提供资金，或支付参与活动费用。
- 贡献者负责为活动创造实际贡献。
- Agent 负责辅助评分和生成贡献证明。
- Cobo Agent Wallet 负责审核 Agent 评分证明所生成的资金分配权，并约束、执行和审计 Agent 的链上资金动作。
- 合约资金池负责沉淀资金、锁定评分结果并按公式执行最终分账。

## 3. 三个角色

### 3.1 项目方 / 用户

项目方 / 用户是活动的资金参与方。

这里的“项目方”和“用户”可以先合并成同一类入口，因为他们在产品里的主要动作都和资金参与有关：

- 项目方可以给自己发起或支持的活动注资。
- 普通用户可以支付参与活动的费用。
- 他们都可以查看活动资金池、活动说明、轮次、贡献评分和结算进度。

项目方 / 用户应该能看到：

- 活动列表。
- 活动标题、活动描述、轮次。
- 活动当前状态。
- 活动资金池金额。
- 自己可以注资或支付参与费用的入口。
- 活动贡献者评分和分账预览。
- 活动是否已经结束、是否已进入分账。

项目方 / 用户不应该负责：

- 新开链上资金池。
- 关闭资金池。
- 配置 Cobo Treasury。
- 查看或处理底层审计日志。

这些属于管理者。

### 3.2 贡献者

贡献者是为活动创造价值的人。

贡献不只包括代码，也包括活动组织和传播：

- 为活动开发代码、修复 bug、提交 PR。
- 搭建活动页面、工具、合约或 Agent 能力。
- 组织活动流程、维护报名和沟通。
- 宣传活动、撰写文章、制作教程、邀请参与者。
- 提供设计、运营、评审、文档等支持。

贡献者应该能看到：

- 可参与的活动。
- 已结束的活动。
- 活动资金池金额。
- 自己在每个活动中的分数。
- 自己预计可获得的分账。
- 自己已经领取多少。
- 自己总共已领取多少。

贡献者可以做：

- 提交贡献证明。
- 查看贡献评分。
- 活动结束后领取分账。

贡献者不应该看到：

- 项目方注资管理。
- 管理者创建或关闭资金池。
- Cobo Treasury 管理和审计操作。

### 3.3 管理者

管理者是活动和资金池的配置与结算负责人。

管理者负责把一个活动正式登记到系统里，并把它映射成可结算的资金池和轮次。

管理者负责：

- 创建活动。
- 填写活动标题。
- 填写活动描述。
- 设置活动轮次。
- 为活动新开资金池。
- 管理活动和链上 `projectId / roundId` 的对应关系。
- 在活动结束时关闭资金池。
- 查看 Cobo Treasury、Agent 决策和审计日志。

管理者应该能看到：

- 所有活动。
- 待创建资金池的活动。
- 待注资或资金异常的活动。
- 评分中、待关闭的活动。
- 已结束活动。
- 每个活动的资金池状态、总分、贡献者数量。
- Cobo Treasury 状态和待审批操作。
- Agent / Cobo 审计记录。

管理者不等于普通项目方。

即使某个项目方发起了活动，链上创建资金池、关闭资金池和 Treasury 操作也应该在管理者工作台中处理，避免项目方页面继续混入 `owner`、`contractOwner`、Cobo Operator 等概念。

## 4. 核心业务对象

### 4.1 活动 Activity

活动是用户看到的主对象。

一个活动至少包含：

- 活动标题。
- 活动描述。
- 活动状态。
- 活动创建者或项目方。
- 活动轮次。
- 对应资金池。

页面上应该优先说“活动”，而不是优先说 `projectId / roundId`。

### 4.2 轮次 Round

轮次是活动的结算周期。

一个活动可以有一个或多个轮次，例如：

- 第一轮报名。
- 黑客松主赛期。
- 宣传结算轮。
- 维护结算轮。

每个轮次可以对应一个独立资金池或一个合约中的独立 `projectId / roundId`。

### 4.3 资金池 Pool

资金池是活动资金的结算容器。

资金池的来源可以包括：

- 项目方注资。
- 用户支付参与活动费用。
- 赞助资金。
- 未来可能接入的外部支付或协议收入。

当前实现里，可以先把“注资”和“支付参与活动费用”统一抽象成资金池入账；后续再根据业务需要区分 `funding` 和 `participationFee` 两种资金来源。

### 4.4 贡献 Contribution

贡献是贡献者为活动创造的价值记录。

贡献可以来自：

- 代码。
- 文档。
- 宣传。
- 组织。
- 设计。
- 评审。
- 社群运营。

贡献记录需要包含：

- 贡献者地址。
- 贡献标题。
- 贡献说明。
- 证据链接。
- Agent 评分。
- Cobo 审核 / 授权后的评分证明。
- 绑定的活动和轮次。

### 4.5 分账 Settlement

分账是活动结束后的资金分配过程。

基本规则：

```text
贡献者分账 = 资金池金额 * 贡献者分数 / 总贡献分数
```

活动未结束时，贡献者可以看到预估分账；活动结束并关闭资金池后，贡献者可以领取实际分账。

### 4.6 Cobo Agent Wallet

Cobo Agent Wallet 不是第四类前端用户，而是系统权限层。

在 CGHub 里，Cobo 的核心作用不是重新判断贡献内容值多少分，而是审核并约束 Agent 把评分结果变成链上资金分配依据的过程。

具体审批规则见：[`AI评分与Cobo审批策略.md`](AI评分与Cobo审批策略.md)。

因为分账公式是：

```text
贡献者分账 = 资金池金额 * 贡献者分数 / 总贡献分数
```

所以 **审核评分就是审核资金分配权**。

Cobo 主要负责：

- 审核 / 授权 Agent 评分证明能否签名或上链。
- 通过 Pact / Policy 限制 Agent 能调用哪些合约、执行哪些动作。
- 通过 `contractCall` 执行贡献记录和自动领取等链上动作。
- 资金池注资的主路径仍然可以是项目方 / 用户钱包；CAW Treasury 注资只是可选的资金管理路径。
- 记录 Cobo tx id、allow / deny、pending approval、Pact 状态等审计信息。
- 隔离前端与 CAW API Key、Wallet UUID、Pact key、Agent 私钥等敏感凭证。

Cobo Pact 在当前实现中按动作拆分，而不是让一个 Main Pact 覆盖所有权限：

| Pact | 作用 | 典型动作 |
|------|------|----------|
| Main Pact | 主线链上执行 | `recordContributionBySig`、`claimFor` |
| Sign Pact | 评分证明签名与风险审批 | EIP-712 `ContributionProof` / `ContributionReviewApproval` 的 `messageSign` |
| Fund Pact | 可选 CAW Treasury 注资 | `USDC.approve`、`fundRound` |
| Guard Pact | 护栏演示和审计证据 | 原生 transfer 的 `deny_if.amount_gt` |

这样 Cobo 的价值不是“代替后端发交易”，而是把评分签名、评分上链、可选注资、超额转账拦截拆成可分别审批、可分别审计、可分别撤销的权限面。

Cobo 不负责：

- 直接判断某条贡献内容的真实价值。
- 替代管理者对异常贡献做业务复核。
- 在 `claimFor` 阶段重新决定资金归属。

`claimFor` 是机械领取动作：评分上链并 finalize 后，贡献者可领金额已经由合约公式确定。任何人触发 `claimFor`，资金都只能发给该贡献者。因此，`claimFor` 不需要 Cobo 做同级别审核；用 CAW 触发它的价值主要是自动化、代付、统一审计和演示证据链。

## 5. 产品主流程

### 5.1 管理者创建活动和资金池

```text
管理者填写活动标题、描述、轮次
-> 管理者创建资金池
-> 系统生成 projectId / roundId
-> 活动进入可注资 / 可参与状态
```

### 5.2 项目方 / 用户提供资金

```text
项目方选择活动
-> 给活动资金池注资

或

用户选择活动
-> 支付参与活动费用
-> 费用进入活动资金池
```

### 5.3 贡献者提交贡献

```text
贡献者选择活动
-> 提交代码 / 宣传 / 组织等贡献证明
-> Agent 评分
-> Cobo 审核 / 授权评分证明
-> 评分证明上链，形成资金分配权
-> 贡献记录绑定到活动轮次
```

### 5.4 管理者结束活动

```text
活动结束
-> 管理者检查贡献评分和资金池
-> 管理者关闭资金池
-> 分账金额固定
```

### 5.5 贡献者领取收益

```text
贡献者进入已结束活动
-> 查看自己的分数、待领取、已领取
-> 自助领取，或由 CAW 自动触发 claimFor
```

## 6. 页面入口

首页先说明完整的活动结算链路，再引导用户进入对应角色工作台：

```text
管理者创建活动资金池
-> 项目方注资、用户付费或其他活动收入进入资金池
-> 贡献者提交证据
-> AI 按 rubric 评分，高风险进入 Cobo App 审批
-> CAW 写入链上贡献分
-> 管理者关闭活动结算
-> 贡献者通过 gasless claim 领取收益
```

首页入口保持三角色清晰分离：

```text
我是项目方 / 用户
进入活动资金参与页，查看活动资金池并注资

我是贡献者
进入贡献和领取页，提交证据并领取收益

我是管理者
进入活动和资金池管理页，创建活动、关闭结算并查看审计记录
```

推荐路由：

| 角色 | 路由 | 页面目标 |
|------|------|----------|
| 项目方 / 用户 | `/project` | 查看活动，注资或支付参与费用 |
| 贡献者 | `/contributor` | 查看活动、提交贡献、领取分账 |
| 管理者 | `/manager` | 创建活动资金池、关闭资金池、管理审计 |

## 7. 权限与产品身份

入口选择是产品身份，不是链上权限。

真实权限仍然要由钱包和后端校验：

- 管理者是否能创建资金池，要看是否具备合约管理员或后端管理权限。
- 管理者是否能操作 Cobo Treasury，要看 Cobo Operator / Agent 服务端配置。
- Agent 评分证明能否成为链上分配依据，要看 Cobo 授权、Agent 签名和合约验签是否通过。
- 项目方 / 用户是否能支付费用，要看钱包连接和资金状态。
- 贡献者是否能领取分账，要看该活动是否已关闭，以及自己是否有待领取金额；领取动作本身不重新决定资金归属。

不要再把这些概念混成一个 `owner`：

- `projectOwner`：项目方或活动业务负责人。
- `contractOwner`：合约管理员。
- `coboOperator`：服务端 Cobo 操作者。
- `contributor`：贡献者。
- `participant`：支付参与活动费用的普通用户。

## 8. 当前 MVP 和后续扩展

当前 MVP 已经具备的主线：

- 多活动 / 多轮次资金池。
- 贡献提交。
- Agent 评分、Cobo 授权和贡献证明签名。
- 链上贡献记录。
- 资金池注资（项目方 / 用户钱包为主；可选 CAW Treasury 路径）。
- 关闭资金池。
- 贡献者自助领取或 CAW 自动触发领取。
- 项目方、贡献者、管理者三入口工作台。

建议后续补强：

- 活动创建表单：管理者直接填写标题、描述、轮次。
- 用户支付参与活动费用：从“注资”中拆出单独支付类型。
- 活动详情页展示报名 / 参与状态。
- 贡献类型细分：代码、宣传、组织、文档、设计、评审。
- 项目方 / 用户的支付记录和参与记录。
- 管理者活动配置审计。

## 9. 最终项目定位

CGHub 不是单纯的资金池页面，也不是单纯的贡献提交表单。

它的产品定位是：

```text
面向活动型协作组织的贡献结算平台。
```

三个用户角色与系统权限层各自清楚：

- 项目方 / 用户：为活动提供资金或支付参与费用。
- 贡献者：为活动贡献代码、组织和宣传等价值。
- 管理者：创建活动资金池、维护活动信息、关闭资金池并监管结算。
- Cobo Agent Wallet：审核 Agent 评分生成的资金分配权，并约束、执行和审计 Agent 的链上资金动作。

只要这三个用户角色不再混在一个页面里，同时把 Cobo 明确为权限层而不是普通用户角色，活动、资金、贡献和分账的逻辑就会清楚很多。
